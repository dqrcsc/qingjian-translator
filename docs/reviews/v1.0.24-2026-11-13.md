# v1.0.24 功能一致性与可靠性复查

日期：2026-11-13。版本基线：`v1.0.24` / `be3dd6e0d3fb99dced4dd4055480296cc95f5f29`。

本轮是审查，不包含运行代码修复、提交、推送或发布。新增文件仅为报告、诊断脚本和证据。优先级综合考虑内容损失、触发频率、用户可见性和恢复成本。

## 结论

v1.0.24 的主要功能已经有实现，既有回归也全部通过。网页仅译文、全宽纯译文、规则表格、公式渲染、会话级站点暂停、请求取消并非空壳；上一轮修复不应因发现新边界问题而被整体否定。

但现有用例没有覆盖几类重要组合和数量边界。本轮额外探针确认 **5 个功能问题：2 个 P1、3 个 P2**。最需要先处理的是 PDF 内容完整性：公式被误当图中文字，以及有效图文标签被静默丢弃。另列出 3 组优化/说明建议，明确区分源码观察与实测故障。

没有在本轮确认到 P0 问题。这不等同于完成安全认证，也不表示任意网站、论文和模型均已验证。

## P1-1：公式被图框吞入，位图文字识别反而被跳过

**证据等级：真实 PDF 入口复现。**

- 输入：丰富正文文字层 → 独立的 Attention 分式公式 → 带 20 条英文标签的 JPEG 图 → 图注。公式与图片在原 PDF 中没有重叠。
- 实际：提取结果没有独立 `equation` 块。插图的矢量标签却变成 `Attention(Q, K, V) = softmax( √`；实际工作台公式块数为 **0**、图像识别请求数为 **0**，图中文字显示 **1 处**，总状态为“全部 1 页翻译完成”。
- 影响：公式失去独立结构，部分公式内容进入文字覆盖流程；真正的位图标签没有翻译。左侧原 PDF 仍在，不能据此认为右侧内容完整。此问题也影响依赖该块模型的后续导出。
- 根因：图注上方区域的启发式搜索没有可靠地排除公式，随后消费图框内文本；又以“存在一个矢量文本组”作为跳过位图识别的条件。
- 位置：[图框搜索及文本消费](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/pdf-engine.js#L1800)、[矢量/位图路径选择](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L2392)。

**建议最小修复：**先保护可信的独立公式/编号区域，再确定图框；不要仅凭一个矢量标签就判定整幅图已覆盖。图框置信度不足时保留原图与公式并提示待处理，避免自动覆盖疑似公式。混合矢量/位图补识别需明确去重，避免无条件给所有图追加一次模型请求。

**验收：**同页无图、图上方有公式、图下方有公式、双栏相邻图、混合矢量/位图分别覆盖；断言公式结构与编号保留、图中文字确实进入处理路径、屏幕/HTML/打印一致、无法完整处理时不显示无条件完成。

当前 README 已承认复杂图框和混合标签有局限；这不是完全未披露的功能。但它涉及科学内容的改写与遗漏，应优先修复，不能只增加免责声明。

## P1-2：有效图文标签超过 16 条时静默丢失

**证据等级：真实 PDF → 后台视觉响应 → 屏幕 → HTML 下载复现。**

- 输入：模型成功返回 **20 条**有效、互不重叠的中文译文区域。
- 实际：工作台只显示 **16 处**；HTML 含第 16 条译文，不含第 20 条；没有“未完成”提示，顶部仍显示全部完成。
- 根因：`normalizeFigureLabelsToCrop()` 在清洗后执行 `cleaned.slice(0, 16)`；后续完整性检查比较的是已经截断后的数组与绘制结果，无法发现原始 20 条只剩 16 条。
- 位置：[标签截断](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/pdf-engine.js#L1039)、[完整性比较](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L2448)。

**建议最小修复：**保留全部有效标签；如确有性能预算，应显式返回原始数、有效数、成功数及省略原因，显示部分完成并提供继续处理入口。数值刻度过滤、重复框过滤与“超过数量上限”不能都无声地归为成功。

**验收：**0/1/16/17/20/50 条边界；验证不重叠有效框不被截掉，屏幕与 HTML 均保留最后一条；过滤或失败时的覆盖率/状态准确。两种协议都应从真实入口经过相同检查。

## P2-1：未翻译 PDF 可以导出空白 Markdown，部分页导出缺少范围声明

**证据等级：空白导出已通过真实入口复现；部分页遗漏由同一路径源码确认。**

- 上传一页 PDF，等待加载完成但不开始翻译，点击导出 Markdown。
- 实际下载内容只有 **一个 UTF-8 BOM，即 3 字节**，没有正文、未翻译提示或范围说明；界面也未阻止此次导出。
- 根因：PDF 按需解析时未处理页面尚无 `blocks`；MD 导出只遍历 `currentDoc.blocks`。部分页面处理后，同一路径只输出已有块，没有总页数和缺页记录。
- 对比：HTML 已生成未翻译页提示，PDF 导出有范围确认，MD 没有统一采用这些信息。不能把“HTML 导出完整性已修复”推断成所有格式均有同等保护。
- 位置：[MD 导出入口](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L3276)、[HTML 的页占位策略](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L1526)。

**建议最小修复：**没有可导出的内容时禁用对应格式并说明原因；部分 PDF 导出明确提示已处理页与缺页，或在文件中保留页占位。不要为补齐导出而悄悄触发整篇收费翻译。EPUB 等其他格式使用同一覆盖范围检查，但本轮没有将其宣称为已独立复现的空文件故障。

**验收：**未开始、一页成功一页未处理、中间页失败、完成全部页四种状态；核对实际下载文件、缺页标记及不新增模型请求。

## P2-2：超过 20,000 条的字幕轨被截断，搜索与 SRT 同时缺尾部

**证据等级：真实内容脚本接收入口、搜索及下载复现。**

- 向实际字幕接收入口交付 **20,001 条**有效 cue。
- 搜索最后一条：结果 **0 行**。侧栏只写“已加载字幕轨道：20000 条”，没有说明已丢弃 1 条。
- 实际下载 `Audit long track.bilingual.srt`：**20,000 个时间区间**，最后一条缺失，文件名没有局部覆盖标识。
- 根因：接收时 `.slice(0, 20000)` 截断源数据；导出判断部分覆盖只考虑观察兜底和音频来源，没有记录轨道截断。
- 位置：[接收截断](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/content/content-main.js#L3481)、[覆盖提示](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/content/content-main.js#L3339)、[导出部分覆盖判断](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/content/content-main.js#L4393)。

**影响范围：**主要是超长视频、直播回放或碎片较多的字幕轨，并非所有日常视频。README 的“全部已加载”按字面可以解释为截断后的集合，但用户不知道接收时已丢失数据，现有虚拟化不代表源数据完整。

**建议最小修复：**保留全部源 cue 并仅限制 DOM；若保留数据预算，则记录 received/retained/dropped，明确截断位置，导出标注 partial，允许分段读取或导出。

**验收：**19,999/20,000/20,001 条边界；首尾搜索、尾部跳转、SRT/TXT/复制一致，DOM 仍不超过窗口上限。另加畸形 cue 和超长单句，不能仅限制条数而放任总字节。

## P2-3：“完整段落语境”实际只发送前 600 字符，段尾选词缺少所在句

**证据等级：实际选区 → 精解按钮 → 后台 HTTP 提示词复现。**

- 输入为 **1,693 字符**段落，在第 **1,660** 字符处选中 `bank`；所在句为 `The river bank was flooded after the storm.`。
- 发给模型的 `Selected Text` 是 `bank`，但 `Surrounding Context Paragraph` 只有段落前 600 字符，完全不含 river/bank/flooded 所在句。
- 影响：服务端即使正常响应，也无法依据正确的局部语境区分“河岸/银行”。本轮证明的是提示词丢失语境，没有以模拟模型输出声称实测发生了错误翻译。
- 根因：固定 `.slice(0, 600)`，没有以选区位置为中心截取。
- 位置：[上下文取样](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/content/content-main.js#L3075)、[提示词拼接](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/background/gemini-client.js#L771)、[README 完整段落宣称](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/README.md#L306)。

**建议最小修复：**短段落完整发送，长段落使用包含选区及前后句的有界窗口；通过 Range 确定偏移，不能简单 `indexOf` 匹配重复词。文案改成“结合所选位置附近上下文”，除非确实提供完整段落。

**验收：**段首/中/尾、同词重复、嵌套链接/强调、跨文本节点、中文长段落、生成译文节点混入等场景；检查实际 HTTP 提示词包含选中位置附近的正确句子。

## 后续优化与说明建议

### P2：长 PDF 右侧阅读区仍缺少页级窗口和增量更新

这是**源码确认的扩展性风险，未在本轮测量到具体内存泄漏或卡顿数值**。

左侧 PDF 预览已做并发和缓存预算，测试验证最多 8 个驻留 render、2 个并发渲染，不能重复宣称旧的 Canvas 回收问题仍未修复。但右侧 PDF 不走普通文档的 100 段窗口：`renderWorkspaceBlocks()` 遍历所有页，重新赋值整段 `innerHTML`；页翻译完成后再次整区重建。已翻译插图的原图/译图 Data URL 也保留在块数据中。

位置：[PDF 与普通文档分支](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L1450)、[整区重建](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L1515)、[页完成刷新](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/studio/studio.js#L2506)。

建议先测 50/200/500 页、含图与无图两组：峰值堆内存、DOM 数、一次页完成刷新耗时、滚动长任务。然后按页增量更新，阅读区只挂载当前窗口；模型数据、搜索索引与导出数据保持完整。导出单独遍历全量，不以缩减导出内容换性能。不要把已存在的预览回收重写一遍。

### P2：网络响应体缺少读取过程中的字节预算

这是**源码确认的资源保护缺口，未通过破坏性超大响应测试制造崩溃**。

`fetchWithTimeoutAndRetry()` 在时间预算内直接 `res.arrayBuffer()` 读取整个响应体，再构造新的 Response。网页图片虽有 20MB 上限，但检查发生在完整读取之后；模型响应亦无同等流式字节计数。时间上限不能限制高速响应的体积。

位置：[完整缓冲响应体](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/background/gemini-client.js#L311)、[图片读取后才检查大小](https://github.com/dqrcsc/qingjian-translator/blob/v1.0.24/background/gemini-client.js#L1238)。

建议给图片和模型 JSON 使用不同的字节预算，在 `ReadableStream` 读取过程中计数并取消超限 body；Content-Length 仅用于提前拒绝，仍验证实际字节。补齐无 Content-Length、伪造较小长度、持续流、超大错误页及取消后不重试的测试。保留已有总时间预算和响应体取消，不引入第二套冲突计时机制。

### P3：说明和测试组织应围绕边界收敛
